v.1.7.1
   - Fixed: opening a failing route in the portal showed no results whenever its failures threw nothing, which is every 404 and every handled error. It opened on the exceptions alone. It now opens on the failed requests themselves, with any exception and stack trace beside them, and each row says how many calls it stands for under sampling, so the rows add up to the count on the card. An agent asking why a route fails gets its failures the same way.

v.1.7.0
   - Fixed: crash counts covered only the last 24 hours, and an issue's first seen date was the start of those 24 hours, so a crash Sentry had seen since April read as new and as a fraction of its size. Every card now gives both reaches, everyone since Sentry first saw it and the last 14 days, e.g. "1,353 users since Apr 13 · 308 in 14d", matching what Sentry shows.
   - Fixed: an issue was called new whenever it was missing from the previous check, so a crash that went quiet for a day came back as new. New now means Sentry first saw it since Huginn last looked, and the label comes down once the issue is more than 14 days old.
   - Fixed: a crash already raised as regressed was raised again on every restart.
   - The crash pane lists every unresolved issue seen in the last 14 days, rather than those seen in the last 24 hours, and reads every page of them rather than the first 100. When there are more than one check reads, the status line says so.
   - The crash pane shows alerts first, then the ten crashes that have reached the most people. A switch ranks them over the last 14 days or over all time. Warning and info reports, which the app sends on purpose, are listed apart and never ranked against a crash.
   - Crashes are no longer raised for being widespread. That bar was a share of everyone hit, so a single large warning set it beyond any crash's reach and nothing was raised.
   - A muted crash comes back when its reach over the last 14 days doubles. Mutes saved earlier are measured again at their current size rather than lifted.
   - Fixed: service findings were built on counts scaled up by sampling, so one recorded failed request could show as a route failing every one of dozens of calls. Rules are now judged on requests actually recorded, estimated counts are marked ~, and each card says how many were recorded, the users seen failing, and when it last failed.
   - A failing dependency is one card whatever codes it failed with, and says what share of its calls failed. It was one card per code, each with the sparkline of all of them.
   - The services pane lists findings by kind, each under a heading that says how it is ranked: failing routes, silent resources, failing dependencies, exceptions, then slow routes. A kind with nothing wrong says so rather than being left out. The window every finding is measured over is shown and can be changed in the pane itself, and the pill on a card says only that it is new since the last check.
   - New: exceptions thrown with no failed request behind them, such as in background work or a failure that was caught, are a finding of their own. A failing route already shows what it threw, so these were the ones nothing showed.
   - Fixed: a resource whose traffic was spread across many quiet routes was reported as having no requests at all.
   - Fixed: numbers on service cards followed the machine's regional settings, e.g. "p95 54,0s" and "1 692 calls".

v.1.6.1
   - A Claude Code registration made before 1.6.0, which has Claude Code start this copy of Huginn itself, is moved over to the HTTP address when Huginn starts, with no button to press. A registration pointing at anything else is left alone. Should Claude Code refuse the new entry, the old one is put back rather than leaving none.
   - Fixed: the app and an MCP server started over stdio write the same log, and each wrote over the lines the other had added, so entries went missing.
   - Fixed: stopping Huginn logged an error from its agent address although nothing had gone wrong.

v.1.6.0
   - Claude Code now reaches Huginn over HTTP, at an address on this machine only, and stays connected through an update. It used to start Huginn itself, and an update stopped that copy, which Claude Code never starts again, so every session lost Huginn until it was reconnected by hand. Press Point at this copy under Settings, Agents once to switch over.
   - The address answers only a caller holding the token Huginn hands Claude Code when registering, since any program on the machine can reach a local port. A named HUGINN_PROFILE gets a port of its own.
   - Agents are only reachable this way while Huginn is running. Any other MCP client can still start Huginn itself, and has to be reconnected after an update.

v.1.5.4
   - Fixed: the Update available button disappeared for a few seconds every half hour while Huginn looked for a newer version, moving the Refresh button beside it, and stayed gone if that check failed, even though the downloaded update was still there to install. Once an update is downloaded, later checks run quietly and the button only changes when a newer release replaces it.

v.1.5.3
   - A pull request is numbered !12345 on its card, the way Azure DevOps writes it. It was #12345, which is how a work item is written.

v.1.5.2
   - Fixed: a build card could show an old failure of yours on a branch that had since passed and then failed again in someone else's run, so the card gave the age of the wrong failure. A card now shows where the branch stands: its newest failure, whoever ran it, and it clears when a later run passes.
   - Agents see everything a build card shows: whether an acknowledged failure is being retried, the link to the run under way, and when the failure finished.

v.1.5.1
   - Fixed: a failed build was shown as being retried whenever anything at all was running on its pipeline, even after a later run on the same branch had passed. Builds are now compared within their own pipeline and branch. A failure counts as retried only when a run is under way and the run before it failed, and it is cleared by a pass on its own branch, not by a pass on another.
   - Two branches failing on the same pipeline are now two cards. Only the newest failure per pipeline was shown before, so one failing pull request could hide another.

v.1.5.0
   - New: an agent can ask why a single service finding is happening. Huginn runs the drill-downs behind the finding using its own sign-in and answers over the MCP connection, so an agent can reach the telemetry behind a finding, over the same window Huginn measured, without Azure access of its own.
   - A service finding's open button now opens the portal on the query behind the finding. It used to open the failures or performance blade, which lists every operation the resource has and answers over a different window, so the finding being looked at had to be found again by hand. What opens depends on the kind: a failing route opens the exceptions with their stack traces, a failing dependency opens the exception from the call that used it, and a slow route opens its percentiles over the window.
   - New: opening a finding in the portal explains what the portal does to the link, once. The portal covers the query with its own queries hub, and may show it in Simple mode with the KQL hidden. Neither can be set from a link, so the query looks absent when it is not there to see. The explanation can be turned off from the dialog itself or under Settings, General.
   - Agents are told at connect time where to start, and how Huginn's access relates to their own. An Azure MCP server holds a single identity for its lifetime, which stays invisible until a query fails with what looks like a permission error and is not one.

v.1.4.1
   - A watched Application Insights resource that cannot be read is now named in the services pane. An expired Azure sign-in used to empty the board and leave the pane reporting all clear, which is the one thing a monitor must never say when it cannot see. When no resource at all could be read, the last findings are kept instead of being replaced by an empty list, and the source is marked as needing attention.
   - The panes no longer say all clear before their first check has finished. Crashes and services say they have not been checked yet until there is an answer, which matters most for Application Insights, where the first check takes about 40 seconds.
   - The log is one file per day and the last 14 days are kept. It had no limit before and had grown to 58 MB over five months, which made it slow to open at exactly the moment it was needed. Log files written before this change are left alone rather than tidied away.
   - A build started with HUGINN_PROFILE writes its log inside that profile's folder, so it no longer appends to the installed copy's log.

v.1.4.0
   - Settings is now a list of sections down the left and one section at a time on the right, rather than expanders inside expanders. Each connection carries its state in the list, so a source that needs attention is visible without opening anything, and what is being held back has a section of its own instead of sitting two expanders deep.
   - Routes answering 404 are reported again. Every 404 used to be dropped, which hides a route your client calls and your server does not have. Scanner traffic is held back by its shape instead: many different paths, a handful of calls each, almost all of them not-found. Anything held back is listed, with the rule that hid it and how much of it there was.
   - New: what is held back can be administered rather than only read. An entry can be promoted so it is always reported, or given a rule of its own so it stays hidden; patterns can be added and removed; and anything promoted is listed so it can be taken back.
   - New: every card has an overflow menu. Crashes offer the link and the issue id, pull requests the reference form and the title, builds the link and the branch name, and service findings the query behind the finding. A card marks itself while its menu is open, so "this one" is unambiguous in a list of near-identical rows.
   - Fixed: your own failed builds appeared for one poll and then disappeared on their own. They were only ever asked for as far back as the previous poll, so each failure was returned exactly once and then fell outside the question.
   - Agents are told what is being held back as well as what was reported.

v.1.3.1
   - Fixed: a source whose status already said "Connected" had the word printed twice when an agent asked for the current status, and a resource with no traffic had its name printed twice.
   - The readme described an Azure DevOps-only tool. It now covers Sentry and Application Insights, with setup for each, and the example MCP client configuration is valid JSON rather than a Windows path with unescaped backslashes.

v.1.3.0
   - New: Sentry monitoring. Huginn watches the projects you pick and raises crashes two ways. A crash that is new, has come back after being resolved, or has outgrown a mute is raised because it changed. A crash reaching at least five people and five per cent of everyone affected in the window is raised because it is big, however long it has been there. Each card carries a sparkline of the last twenty-four hours and a phrase for its shape, so a constant drip is told apart from a single burst at a glance.
   - New: Application Insights monitoring. Sign in with your own Azure account and pick the resources you can already see. Huginn reports routes that are failing, routes that are slow at the ninety-fifth percentile, failing dependencies, and resources that have gone silent, ordered by severity rather than by raw magnitude, so routes failing every call no longer sit below merely slow ones. Failing routes name the result code, because whether it is a 500 or a 405 decides what you do next.
   - New: connections are a first-class concept. Azure DevOps, Sentry and Application Insights each hold their own sign-in, their own list of what to watch, and their own status, and each keeps working while the others are broken. Every pane says when it was last checked, and a pane whose source cannot answer says so rather than looking calm.
   - The dashboard is built around what needs acting on now. Pull requests and builds share a column, since neither runs to many rows, leaving crashes and services a full column each. Card actions are icons with tooltips instead of words, which is what gives the titles room to be read.
   - Notifications are summarised per poll. A check that turns up ten new items used to fire ten separate toasts; it now fires one that names the count and what is in it. A single item still gets the detailed notification it always did.
   - New: Huginn can answer an AI coding agent asking what is currently broken. Settings has an Agents section that registers it with Claude Code in one press, and prints the command and configuration for any other MCP client. Reading needs no extra sign-in and opens no network port.
   - Settings written by a different version of Huginn are no longer discarded. Saving used to drop anything the running build did not recognise.
   - Settings are saved when you close the panel or the window, rather than only on an explicit save, so an edit interrupted by a restart is no longer thrown away.
   - Set HUGINN_PROFILE to give a build its own settings, credentials and state, so a second copy on the same machine shares nothing with the first.
   - Fixed: long pull request titles drew over the buttons beside them, and long build names were cut off mid-character instead of trimming.
   - Upgraded Avalonia to 12.1.2.

v.1.2.0
   - Bumped System.Drawing.Common from the transitive 4.7.0 to 9.0.0, clearing the GHSA-rxg9-xrhp-64gj critical-severity advisory that the release builds were flagging.
   - Rooted the Windows toast-notification dependency chain (Microsoft.Toolkit.Uwp.Notifications, Microsoft.Windows.SDK.NET, WinRT.Runtime) so the trimmer no longer strips reflection-only members on best-guess heuristics. The current call sites worked in practice, but any new toast template or WinRT activation path is now safe by construction rather than by luck.
   - Cleaned up the trim warnings the release builds had been logging: removed an unused Avalonia-template stub (DisableAvaloniaDataAnnotationValidation) Huginn never needed; the runtime platform dispatcher's [DynamicDependency] hints are now guarded so each TFM only references types that actually exist in it; the remaining safe-but-unprovable Type.GetType(string) calls in the dispatcher and the view locator carry explicit [UnconditionalSuppressMessage] justifications. The three IL2104 warnings from the rooted Windows toast/WinRT assemblies stay visible on purpose so a new noisy dependency wouldn't be silently swallowed.

v.1.1.0
   - New: Updates section in Settings shows the running version, lets you trigger a manual update check, and displays the release notes for the next version once it has been downloaded. A "Restart now" button appears alongside the notes so you can apply the update on demand instead of waiting for the next launch.
   - The toolbar "Update available" button now lives next to a much more discoverable Settings home for the same actions.

v.1.0.0
   - First stable release. Velopack auto-update is now wired end-to-end: the app polls GitHub Releases every 30 minutes, downloads new versions in the background, and applies them on next launch. The toolbar "Update available" button is a one-click install-and-restart that shuts Avalonia down gracefully so settings persist across the patch.
   - Retired the legacy update check that compared the embedded build timestamp against the ADO repo's latest commit — Velopack replaces it entirely.

v.0.1.0
   - First public release. Huginn moves from an internal ADO repo to a public GitHub repo at github.com/malforge/Huginn; the app itself continues to monitor Azure DevOps for pull requests and pipeline builds. Velopack-driven auto-update against GitHub Releases replaces the previous "open the repo to update" link.
